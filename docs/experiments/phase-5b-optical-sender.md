# LumaLink Phase 5B — Real Protocol Packets → Optical Sender

## 1. Executive Summary & Objective

Phase 5B transitions LumaLink's optical sender from mock ASCII strings (`FOUNTAIN_8`) to **genuine, canonical LumaLink TransportPacket wire bytes** generated by the TypeScript core.

```
Real Deterministic Binary File (1024 Bytes)
  │
  ▼ [Canonical FileBlocker]
Source Blocks (1 Block, K=16, SymbolSize=64B)
  │
  ▼ [Canonical SenderSession + NodeCryptoProvider]
X25519 Ephemeral Key Agreement + ChaCha20-Poly1305 AEAD + LT Fountain Symbols
  │
  ▼ [Canonical BinaryPacketCodec]
Validated TransportPacket Wire Bytes (122 Bytes per Packet, Magic 'LUMA', CRC-32)
  │
  ▼ [Static Browser Fixture: scripts/display-harness/real-packets.js]
Raw Uint8Array Wire Bytes (No Base64, No Hex)
  │
  ▼ [Browser Display Harness + qrcode.min.js]
ISO/IEC 18004 8-Bit Byte Mode QR Symbol
  │
  ▼ [Physical Monitor Display]
Physical Optical Channel (Airgap)
  │
  ▼ [Android CameraX + ZXing QR Reader]
Raw Decoded Byte Payload Extracted
  │
  ▼ [Physical Verification]
Verify Magic == 'LUMA' (0x4C554D41) & Verify Header Layout & Verify IEEE 802.3 CRC-32
```

## 2. Four Operational Tiers & Scope Demarcation

To maintain strict scientific and architectural discipline, LumaLink distinguishes four distinct operational tiers:

| Tier                                          | Environment                                   | Scope                                                                                                                                                                                                    | Verified In                                                     |
| --------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Tier 1: Software E2E**                      | Pure In-Memory / Vitest                       | Full file $\to$ blocking $\to$ LT encoding $\to$ AEAD encryption $\to$ simulated channel impairments (15% drop, 10% dup, reorder) $\to$ AEAD decryption $\to$ LT peeling reassembly $\to$ SHA-256 match. | Phase 5A (`phase5a-real-file-e2e.test.ts`)                      |
| **Tier 2: Simulated Optical**                 | Pure Software / Synthetic Canvas              | Mathematical simulation of display refresh rates (15–30 Hz), camera capture FPS (30 FPS), timing jitter, and synthetic pixel degradation.                                                                | Phase 4 (`optical-pipeline.test.ts`, `phase4-optical.bench.ts`) |
| **Tier 3: Physical QR Decode**                | Physical Screen $\to$ Android Camera          | CameraX capturing physical screen image, detecting QR pattern, and reading raw bytes.                                                                                                                    | Phase 4 / Phase 5B (`OpticalMeasurementReceiverActivity`)       |
| **Tier 4: Physical Protocol Packet Recovery** | Physical Screen $\to$ Camera $\to$ Wire Audit | Extracting physical raw bytes and proving they match the canonical `TransportPacket` wire format byte-for-byte with valid CRC-32 and LUMA magic.                                                         | **Phase 5B Objective**                                          |

> **IMPORTANT BOUNDARY**: Phase 5B does **NOT** claim full physical multi-block file reassembly on Android. Receiver-side decryption, peeling decoder reassembly, and file-level SHA-256 validation on the mobile device belong to subsequent phases. Phase 5B ends at **physical protocol packet recovery**.

## 3. Real Packet Generation Workflow

The packet generator script [`scripts/generate-phase5b-packets.ts`](file:///c:/Users/laksh/OneDrive/Desktop/Luma_Link/scripts/generate-phase5b-packets.ts) executes the canonical pipeline in Node.js:

1. **Deterministic Binary File Fixture**:
   - Reuses the deterministic structured binary approach from Phase 5A: an 8-byte PNG-compatible signature (`0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a`) followed by high-entropy pseudo-random bytes seeded with `0x5b5b5b5b`.
   - File size: $1,024\text{ bytes}$ (exact fit for 1 source block: $K=16 \times 64\text{ bytes}$).
   - SHA-256 digest: `71a402d778ad700a99988d1952a8ea6f55cf570b74eb888d249e2087b0b8c8e0`.

2. **Source Blocking & Session**:
   - `FileBlocker` (`symbolSize: 64, symbolsPerBlock: 16`) partitions the file into 1 source block with $K=16$.
   - `SenderSession` (`mode: 'quick'`, `NodeCryptoProvider`) establishes session keys via X25519 ECDH and HKDF-SHA256.
   - **Cryptographic Freshness**: The session keys and UUID v4 session ID are generated fresh per generator run using OpenSSL CSPRNG. The resulting wire bytes and CRC-32 differ across generator invocations, while the fixture `real-packets.js` freezes a single valid session snapshot for browser playback.

3. **LT Encoding & AEAD Encryption**:
   - `LtEncoder` samples Robust Soliton degree and neighbors from deterministic seed `(blockIndex, symbolId)`.
   - `SessionSecurityContext` encrypts each symbol with ChaCha20-Poly1305 using deterministic 12-byte nonces and AAD binding to header metadata.
   - Encrypted payload size: $64\text{B symbol} + 16\text{B Poly1305 MAC} = 80\text{ bytes}$.

4. **Wire Serialization & Checksum**:
   - `BinaryPacketCodec.encode()` prepends the 42-byte header and appends IEEE 802.3 CRC-32 over bytes 0..37 + payload.
   - Total wire packet length: $42 + 80 = 122\text{ bytes}$.

5. **Fountain Overhead Configuration**:
   - Configured overhead factor: $2.4\times$.
   - Transmitted symbol count: $\lceil K \times 2.4 \rceil = \lceil 16 \times 2.4 \rceil = 39\text{ packets}$.
   - Note: The factor $2.4\times$ is a sender transmission budget for optical loss absorption, **not** an algorithmic requirement of the LT decoder.

6. **Self-Validation**:
   - Every single generated packet is immediately decoded with `BinaryPacketCodec.decode()`, validating magic `'LUMA'`, version 1, type DATA (2), `FLAG_ENCRYPTED` (0x02), session ID, block index, symbol ID, degree, payload length, and CRC-32.

## 5. Diagnostic Sender HUD

The browser HUD extracts real metadata from the 42-byte binary header of each displayed packet:

```
Frame 1/39 | Blk 0 | Sym 0 | K=16 | deg=1 | 122 B | Session afe45788... | 66 ms (15 Hz) | R=1
```

- **Blk**: Block index (uint32).
- **Sym**: Fountain symbol ID (uint32).
- **K**: Number of source symbols in block (uint16).
- **deg**: LT Soliton degree of the symbol (uint16).
- **B**: Complete serialized wire size in bytes (122 B).
- **Session**: First 8 hex characters of the 16-byte UUID session ID.
- **Timing & R**: Presentation interval (66 ms / ~15 Hz) and repetition factor ($R=1, 2, 3$).

## 6. Physical Validation Protocol & Observed Behavior

### Test Parameters

- **Sender**: Computer monitor displaying `scripts/display-harness/index.html`.
- **Receiver**: Google Pixel 7 running `OpticalMeasurementReceiverActivity`.
- **Target Distance**: $0.3\text{ m} - 0.5\text{ m}$.
- **Resolution**: $1280 \times 720$ (720p) Y-plane luminance capture.
- **QR Properties**: Version 7, ECC Level M, Scale 8 (424px).
- **Interval**: 66 ms (~15 Hz), Repetition $R=1$ and $R=2$.

### Physical Verification Criteria & Byte Delivery

1. **Camera Arrival & Frame Delivery**: CameraX delivers 720p camera frames at ~30 FPS without unhandled exceptions.
2. **QR Optical Detection**: Android ZXing detects the QR code symbol in 8-bit Byte Mode across presentation intervals.
3. **Payload Extraction**:
   - In ISO/IEC 18004 8-bit Byte Mode, ZXing provides the decoded byte payload in `ResultMetadataType.BYTE_SEGMENTS` (or accessible via ISO-8859-1 byte mapping), matching the $122\text{-byte}$ complete wire packet.
   - (Note: ZXing's raw codeword stream `result.rawBytes` returns 196 total codewords including Reed-Solomon parity; the unpadded transport packet payload is contained in the byte segment).
4. **Wire Format Properties**:
   - Magic: `rawPayload[0..3] == [0x4C, 0x55, 0x4D, 0x41]` ('LUMA').
   - Layout: 42-byte header with $K=16$, valid block/symbol indices, and 80-byte encrypted payload.
   - Integrity: IEEE 802.3 CRC-32 matches checksum field.
5. **Phase Demarcation**:
   - The Phase 5B Android harness measures camera timing, decode latency, and duplicate classification. Full in-app Kotlin protocol header decoding, AEAD decryption, and LT reassembly are scheduled for Phase 5C.

## 7. Limitations & Future Phases

- **Receiver Decryption**: Android receiver currently extracts and validates wire packets; mobile-side AEAD decryption and fountain peeling decoding are deferred to Phase 5C.
- **Browser-Side Encryption**: Generating encrypted packets requires `NodeCryptoProvider` (`node:crypto`). Running the sender in a browser without Node requires a browser-compatible `CryptoProvider` implementation (e.g. `@noble/ciphers` + `@noble/curves`), to be evaluated under a future ADR.
